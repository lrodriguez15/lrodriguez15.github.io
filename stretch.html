Stretch problems

if the session was easy no grade bring them to asesorías

What these are. Every lecture ends with three problems written so that already knowing Python does not help much: proofs about the minimum number of steps, specifications with holes in them, exhaustive checks, instructions executed by a literal friend. They are not graded — the course weights are fixed by the academia — and they are not homework. The reward is the conversation: bring your answer to asesorías (Tue / Thu / Fri 16:30–17:30) or drop a photo in the week's evidence box on Canvas.

The same problems also live at the end of each lecture page, under Stretch — if the session was easy. This page just collects them. New set every session.

Lecture 01 — Algorithms and Programs Week 1 · Tue 22 Sep

Open the lecture →

Optional, ungraded, and harder than they look. Bring them to asesorías or leave them in the week’s evidence box. No Python needed — none of these is a programming problem.

  1. Seven questions. I think of a whole number from 1 to 100; you may only ask questions I answer yes or no. Write the algorithm — numbered steps, no gaps — that always finds the number in seven questions or fewer. Then argue, on paper, why six can never be enough. (Count what six yes/no answers can distinguish.)
  2. Euclid, executed. The oldest algorithm still in daily use: to find the largest number that divides both a and b, replace the larger by the difference until both are equal. Write it as INPUT / OUTPUT / steps. Execute it by hand for (48, 18) and for (1071, 462), counting the steps. Then answer the only question that matters for an algorithm: why must it stop?
  3. The literal friend. Write instructions for drawing a five-pointed star with one continuous line. Give them to someone who follows them literally and says nothing. Every point where they hesitate or draw something else is a missing line in your algorithm — write those lines. How many did you need?

Lecture 02 — From Algorithm to Program Week 1 · Fri 25 Sep

Open the lecture →

Optional, ungraded, harder than they look. Bring them to asesorías or leave them in the week’s evidence box.

  1. Average without a memory. Today’s program stored three speeds and averaged them. Suppose you could only keep two numbers: the average so far and how many measurements went into it. Show that new_avg = old_avg + (x - old_avg) / n gives the same result as adding everything up, then write the three-measurement program that way and test it with the same inputs. Which version would you trust with a million measurements, and why?
  2. Two averages that disagree. (v1 + v2 + v3) / 3 and (d1 + d2 + d3) / (t1 + t2 + t3) are both called “average speed”. Find distances and times where they differ by a factor of more than two. Then say, in one sentence each, which one a traffic officer wants and which one the driver wants.
  3. Predict, then run. Write down, before running anything, what Python prints for 7 // 2, -7 // 2, 7 % -2, 2 ** 3 ** 2, 0.1 + 0.2 == 0.3, and "3" * 3. Run them. For every miss, write the rule you were missing — that rule is a line in someone’s quick exam.

Lecture 03 — Conditionals Week 2 · Tue 29 Sep

Open the lecture →

Optional, ungraded, and harder than they look. Bring them to asesorías or leave them in the week’s evidence box.

  1. No if. Write speed_label(speed) (slow / normal / fast / too fast, same thresholds as the in-class activity) without if, elif, else or the conditional expression. Hint: True + True is 2. Then say, in one sentence, why the if version is still the one you should hand in.
  2. The specification hunt. Take the client-status table from Friday’s lab (más de $1,000,000 → Excelente, …). List every input the table does not decide: the exact limits, negatives, decimals, text. That list is the algorithm’s missing lines; write them.
  3. Prove the leap year. Write the condition as one boolean expression and as nested ifs, and show they agree for every year from 1 to 2400. You may use anything you already know; the point is the word every.

Lecture 04 — Functions Week 2 · Fri 2 Oct

Open the lecture →

Optional, ungraded, harder than they look.

  1. Count the comparisons. descending(a, b, c) — what is the minimum number of comparisons that always suffices to order three numbers? Write a version that never uses more than that, and argue (on paper) why fewer is impossible.
  2. Exhaustive. Write check() that calls classify_triangle(a, b, c) for every integer triple with sides 0–10 and counts how many land in each label. What fraction are “not a triangle”? Is there any triple where your function and a friend’s disagree?
  3. A function that takes a function. apply_twice(f, x) returns f(f(x)). Try it with fahrenheit_to_celsius. What does the result mean, and why is that a warning about what a function’s parameters promise?

Lecture 05 — The while loop Week 3 · Tue 6 Oct

Open the lecture →

Optional, ungraded, harder than they look. Bring them to asesorías or leave them in the week’s evidence box.

  1. Prove it stops. For each of 02, 03, 05 and 07, write the one quantity that moves toward the exit on every repetition, and the value at which the loop ends. Then write a loop whose test does change every turn and which still never ends. (Hint: a variable that alternates.) Say why your termination argument fails for it.
  2. Backoff, in Python. Implement the opener: attempts from 1 to 16, a waiting range that doubles (limit = limit * 2), and random.randint(0, limit) as the wait. Decide “sent” with random.random() < 0.3. Print each attempt. Run it ten times: what is the largest number of attempts you saw, and what is the largest wait? Then answer: why random, and not just “double the wait”?
  3. The 65. In 05_sum_to_n.py, swapping the two lines in the block turns 55 into 65 for n = 10. Without running, write the formula for the wrong answer as a function of n, and check it for n = 1, 2, 3. Then design one test value that distinguishes the two programs and would have caught the bug in a program that only printed the final sum.

Lecture 06 — The while loop, in practice Week 3 · Fri 9 Oct

Open the lecture →

Optional, ungraded, harder than they look.

  1. Euclid, faster. Replace subtraction with %: while b != 0: a, b = b, a % b. Trace gcd(1071, 462) both ways and count the turns. Then argue why the % version also stops — the quantity is different. Which version would you trust with gcd(10**9, 1)?
  2. The binary search guesser. Write robot_play(secret) that plays play’s game without a human: it keeps low and high, always guesses the middle, and counts attempts. Run it for every secret from 1 to 100 (a loop around a loop) and report the maximum attempts. Is it 7? Then make the range 1–1000 and predict the maximum before running.
  3. Reverse, not count. reverse_digits(n) returns the number with its digits reversed — 1234 → 4321, 1200 → 21. Same loop as digits, with % 10 to pull the last digit and an accumulator built with `* 10 +. Then the question: for which inputs doesreverse_digits(reverse_digits(n)) != n`, and is that a bug or the spec?
