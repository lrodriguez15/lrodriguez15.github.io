Smart Pointers and RAII

unique_ptr shared_ptr weak_ptr RAII memory-management

Overview

A smart pointer is a class that wraps a raw pointer and manages the lifetime of the pointed-to object automatically. When the smart pointer goes out of scope it calls delete for you — no manual cleanup required. This is RAII applied to heap memory.

C++14 ships three smart pointer types in <memory>:

Smart pointer Ownership Copyable? Overhead vs raw ptr
std::unique_ptr<T> Sole, exclusive No — move-only Zero (release builds)
std::shared_ptr<T> Shared via reference count Yes — copy bumps the count ~2× pointer: atomic ref-count + control block
std::weak_ptr<T> Non-owning observer of a shared_ptr resource Yes Tracks count separately; no increment on copy

Key Ideas

  • Reach for unique_ptr first. Upgrade to shared_ptr only when you genuinely need shared ownership. Use raw pointers and references as non-owning observers — they are fine and carry no overhead.
  • The rule is about ownership, not about access: a function that merely uses an object should take const T& or T*, not a smart pointer.
  • make_unique<T>(args…) and make_shared<T>(args…) are always preferred over new — they are exception-safe and, for shared_ptr, more efficient (single allocation).
  • weak_ptr does not contribute to the reference count and therefore does not prevent destruction. Always .lock() it before use.

Notes

The problem: raw new/delete leaks on every exit path

Any function that allocates with new must call delete on every exit path — every return, every thrown exception, every branch. Miss one and the memory leaks. In a function with multiple early returns and a try/catch this becomes untenable.

Broken

// BAD — leaks if validate() throws or the early return fires
Widget* make_widget(bool fast) {
    Widget* w = new Widget();
    if (!validate(w)) {
        return nullptr;   // LEAK: w is never deleted
    }
    if (fast) {
        w->turbo = true;
        return w;
    }
    w->init_heavy();
    return w;
}

unique_ptr — sole ownership

std::unique_ptr<T> enforces that one and only one smart pointer owns an object at any time. Its destructor calls delete automatically — even if the function returns early or throws.

  • Cannot be copied. Ownership transfers via std::move.
  • Zero overhead over a raw pointer in release builds.
  • Create with std::make_unique<T>(args…) (available since C++14).

Fixed

// GOOD — unique_ptr: destructor fires on every exit, no manual delete
std::unique_ptr<Widget> make_widget(bool fast) {
    auto w = std::make_unique<Widget>();
    if (!validate(w.get())) {
        return nullptr;   // w's destructor runs here — no leak
    }
    if (fast) {
        w->turbo = true;
        return w;         // ownership transferred to caller
    }
    w->init_heavy();
    return w;
}

Rule of Zero with unique_ptr. When a class owns a resource via unique_ptr, the compiler auto-generates correct move operations and deletes copy — you need no destructor, no copy constructor, and no copy-assignment operator: 

class Car {
    std::string              brand;
    std::unique_ptr<Engine>  engine;   // owns Engine; copy is deleted automatically
public:
    Car(const std::string& b)
        : brand(b), engine(std::make_unique<Engine>()) {}

    void drive() const { engine->run(); }
    // ~Car() not needed — unique_ptr's destructor handles Engine
};

shared_ptr — shared ownership

std::shared_ptr<T> allows multiple owners. An internal control block holds a reference count. The object is destroyed when the last shared_ptr owning it is destroyed or reset.

  • Copyable — each copy increments the ref-count atomically.
  • Slight overhead: atomic increment/decrement on every copy and destroy.
  • Prefer std::make_shared<T>(args…): single allocation for object + control block.
std::shared_ptr<Node> a = std::make_shared<Node>(42);
// use_count == 1
{
    std::shared_ptr<Node> b = a;   // use_count == 2
    std::shared_ptr<Node> c = a;   // use_count == 3
} // b, c destroyed — use_count back to 1
// a destroyed here — use_count → 0 → ~Node() called

The shared_ptr cycle leak — and how weak_ptr breaks it

Two objects can each hold a shared_ptr to the other. Each keeps the other's ref-count above zero, so neither is ever destroyed — a classic reference cycle.

Broken

// BROKEN — cycle: A and B keep each other alive forever
struct A {
    std::shared_ptr<B> b_ptr;
    ~A() { std::cout << "~A\n"; }
};
struct B {
    std::shared_ptr<A> a_ptr;   // <-- this creates the cycle
    ~B() { std::cout << "~B\n"; }
};

int main() {
    auto a = std::make_shared<A>();
    auto b = std::make_shared<B>();
    a->b_ptr = b;   // a's count: 1→still 1 (b owns a from b->a_ptr)
    b->a_ptr = a;   // b's count: 1→still 1
    // main exits: local a and b destroyed, but each object's count drops only to 1
    // ~A and ~B are NEVER printed — the heap objects leak forever
}

Fix: make the back-pointer a weak_ptr. A weak_ptr does not increment the ref-count, so it cannot create a cycle.

Fixed

// FIXED — weak_ptr breaks the cycle
struct B {
    std::weak_ptr<A> a_ptr;   // non-owning; does NOT keep A alive
    ~B() { std::cout << "~B\n"; }
};

// When main exits:
//   local a destroyed → A's strong_count → 0 → ~A → b_ptr (shared_ptr<B>) released
//   → B's strong_count → 0 → ~B
// Both destructors fire. No leak.

weak_ptr — non-owning observer

std::weak_ptr<T> observes a shared_ptr-managed resource without owning it:

  • Does not increment the strong reference count.
  • Must be promoted to a shared_ptr via .lock() before the resource can be accessed.
  • .lock() returns an empty shared_ptr if the resource has already been destroyed — safe to test with if (auto sp = wp.lock()).
std::shared_ptr<int> sp = std::make_shared<int>(100);
std::weak_ptr<int>   wp = sp;

if (auto locked = wp.lock()) {
    std::cout << "value: " << *locked << "\n";  // 100
}

sp.reset();   // drop the last strong owner — object destroyed

if (!wp.lock()) {
    std::cout << "resource is gone\n";
}

Ownership vs observation — the passing rules

Situation Parameter type
Function only uses the object const T& or T* (non-owning)
Function takes sole ownership std::unique_ptr<T> by value
Function shares ownership std::shared_ptr<T> by value
Function observes a shared resource std::weak_ptr<T> or raw T* (non-owning)

Code Examples

Full runnable programs are in examples/. The snippets below are the teaching cut.

unique_ptr basics — create, use, move

#include <memory>
#include <iostream>

class Engine {
public:
    Engine()  { std::cout << "Engine ON\n";  }
    ~Engine() { std::cout << "Engine OFF\n"; }
    void run() const { std::cout << "vroom\n"; }
};

int main() {
    // Prefer make_unique — never spell 'new' here
    auto eng = std::make_unique<Engine>();
    eng->run();

    // Transfer ownership — eng is now null
    auto eng2 = std::move(eng);
    if (!eng) std::cout << "eng is empty after move\n";
    eng2->run();

    // eng2 goes out of scope → ~Engine() fires automatically
}

unique_ptr in a class — Rule of Zero

#include <memory>
#include <string>
#include <iostream>

class Car {
    std::string             brand;
    std::unique_ptr<Engine> engine;
public:
    Car(const std::string& b)
        : brand(b), engine(std::make_unique<Engine>()) {}

    void drive() const { engine->run(); }

    // No destructor, no copy constructor, no copy-assignment.
    // unique_ptr handles cleanup; move is auto-generated.
};

int main() {
    Car c("Toyota");
    c.drive();

    Car c2 = std::move(c);   // Engine ownership moves to c2
    c2.drive();
}

shared_ptr and reference counting

#include <memory>
#include <iostream>

struct Node {
    int value;
    Node(int v) : value(v) { std::cout << "Node(" << v << ") created\n"; }
    ~Node()                 { std::cout << "Node(" << value << ") destroyed\n"; }
};

int main() {
    auto a = std::make_shared<Node>(42);
    std::cout << "use_count: " << a.use_count() << "\n";  // 1
    {
        auto b = a;   // both own the same Node
        std::cout << "use_count: " << a.use_count() << "\n";  // 2
        auto c = a;
        std::cout << "use_count: " << a.use_count() << "\n";  // 3
    } // b and c destroyed — count drops to 1
    std::cout << "use_count: " << a.use_count() << "\n";  // 1
} // a destroyed → count → 0 → ~Node()

shared_ptr cycle (broken) and weak_ptr fix

Broken

#include <memory>
#include <iostream>

struct B;

// --- BROKEN version (cycle, no output from destructors) ---
struct A_broken {
    std::shared_ptr<B_broken> b_ptr;
    ~A_broken() { std::cout << "~A_broken\n"; }
};
struct B_broken {
    std::shared_ptr<A_broken> a_ptr;  // keeps A alive — cycle!
    ~B_broken() { std::cout << "~B_broken\n"; }
};

Fixed

// --- FIXED version ---
struct A {
    std::shared_ptr<B> b_ptr;
    ~A() { std::cout << "~A\n"; }
};
struct B {
    std::weak_ptr<A> a_ptr;   // non-owning — no cycle
    ~B() { std::cout << "~B\n"; }
};

int main() {
    {
        auto a = std::make_shared<A>();
        auto b = std::make_shared<B>();
        a->b_ptr = b;
        b->a_ptr = a;
    } // ~A then ~B both print — no leak
}

Accessing a resource through weak_ptr

#include <memory>
#include <iostream>

int main() {
    std::shared_ptr<int> sp = std::make_shared<int>(100);
    std::weak_ptr<int>   wp = sp;

    // Must lock before accessing
    if (auto locked = wp.lock()) {
        std::cout << "value: " << *locked << "\n";  // 100
    }

    sp.reset();   // destroy the object

    if (wp.lock() == nullptr) {
        std::cout << "resource is gone\n";
    }
}

Exercises

Exercise 1

Zoo (unique_ptr + polymorphism). Implement a Zoo class that owns a collection of Animal objects (use the polymorphic hierarchy from Lecture 03, or define a minimal one here: Animal with a virtual speak(); Dog and Cat overriding it). Store them as std::vector<std::unique_ptr<Animal>>. Add an addAnimal method that takes a unique_ptr<Animal> by value. Implement makeNoise() that calls speak() on every animal via virtual dispatch. Verify — using destructor messages — that all animals are freed automatically when the Zoo goes out of scope with no explicit delete.

Exercise 2

Shared Config (shared_ptr). Create a Config object implemented as std::unordered_map<std::string, std::string>. Two classes, Server and Logger, each hold a shared_ptr<Config>. Demonstrate in main() that:

  • modifying the config through Server's handle is visible through Logger's handle;
  • the config is destroyed only after both Server and Logger go out of scope (use a destructor message in Config to verify).

Exercise 3

Doubly-linked list (shared_ptr + weak_ptr). Build a linked-list node: 

struct ListNode {
    int value;
    std::shared_ptr<ListNode>  next;
    std::weak_ptr<ListNode>    prev;   // back-pointer — must NOT be shared_ptr
    ~ListNode() { std::cout << "~ListNode(" << value << ")\n"; }
};

Insert five integer nodes, traverse forward (via next) and backward (via prev.lock()). Reset the head pointer and confirm — via destructor messages — that all five nodes are freed in order. Explain in a comment why prev must be weak_ptr and not shared_ptr.
