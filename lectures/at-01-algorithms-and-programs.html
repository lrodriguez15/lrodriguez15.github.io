Overview

Day one. Most of this room has never written a program. That is fine — and it is not what we start with anyway.

We start with the one thing that separates a program that works from a program that nearly works: precision. A computer is not a collaborator who fills in what you meant. It is the most literal reader you will ever write for, and it executes exactly what you wrote, including the part you thought was obvious.

So today there is no Python. Today we write instructions in Spanish or English, on paper, and then I execute them adversarially — exactly as written, not as intended — until they break. By the end you will know, physically, why an algorithm needs every step stated, in order, finite, and unambiguous.

That is the whole lesson. One idea.

Notes

What a computer actually is, for our purposes

A machine that executes a sequence of instructions, one at a time, in order, without judgement. It has memory (somewhere to put values), it can do arithmetic, it can compare, and it can choose what to do next based on that comparison. That is the entire vocabulary.

Everything you build this semester is made of those four things. Not more.

Gloss: memoria — memory · instrucción / sentencia — statement · ejecutar — to execute

Algorithm vs. program

Algorithm Program
What it is The thinking The typing
Written in Natural language, pseudocode, a flowchart Python
Read by A human (and, adversarially, by you) A machine
Can be wrong by Being ambiguous, unordered, unending …all of that, plus syntax

Notice the last row. A program can fail for every reason an algorithm can fail, and for reasons of its own. If you skip the algorithm, you are debugging both layers simultaneously, without knowing which one is broken. That is why we separate them, and that separation is the single most useful habit in this course.

The four properties

Finite. It ends. “Keep adding numbers” is not an algorithm. “Keep adding numbers until the user types 0” is. The most common way first-semester code hangs forever is a step that has no stopping condition — we will meet this properly in Week 3, but it starts here.

Ordered. The sequence is part of the meaning. Break the eggs, then heat the pan and heat the pan, then break the eggs are different algorithms with different results.

Unambiguous. Exactly one reading. “Add the numbers” — which numbers? All of them? The last two? In what order? If two people following your algorithm can get different answers, it is ambiguous, and ambiguity is a bug you have not found yet.

Defined input and output. You know what you are given and what you must produce. This is the step students skip. Before writing a single step, write two lines:

INPUT:  the distance in kilometres, the time in hours
OUTPUT: the average speed in km/h

Half the ambiguity dies right there.

Pseudocode — our notation

Pseudocode is structured natural language. There is no official syntax; the convention for this course:

ALGORITHM  average_speed
INPUT:     distance (km), time (hours)
OUTPUT:    speed (km/h)

1. READ distance
2. READ time
3. speed ← distance / time
4. DISPLAY speed
END
  • ← is assignment — “gets the value of”. Not equality. speed ← distance / time is a command, not a claim.
  • READ gets a value from the user. DISPLAY shows one.
  • Steps are numbered. Numbering is not decoration: it is what makes “ordered” checkable.

Gloss: asignación — assignment · pseudocódigo — pseudocode · entrada / salida — input / output

Writing an algorithm that survives a hostile reader

The working method, which is also the exam method and also the method you will use in your final project:

  1. State input and output. Two lines, before anything else.
  2. Write the steps, numbered. One action per step. If a step contains “and”, it is probably two steps.
  3. Attack it. Read your own algorithm as literally as I read your square. Look specifically for: a step that assumes something unstated; two steps whose order you never decided; a quantity you named two different ways; a case where the input is empty, zero, or negative.
  4. Fix and repeat.

Step 3 is the one that separates a passing grade from a good engineer. Everyone can do step 2.

Exercises

Exercise 1

Exercise 1 — Price validation (individual, on paper, 10 min)

Write an algorithm that checks whether a price entered by the user is valid. A price is valid if it is a positive value.

Then attack your own algorithm and answer, in writing, underneath it:

  • What does yours do if the user enters exactly 0?
  • What does yours do if the user enters hola?
  • Does your algorithm say what “valid” looks like as an output — a word, a symbol, nothing?

Nobody’s first version answers all three. That is the point of the exercise.

Exercise 2

Exercise 2 — Metres to feet (pairs, on paper, 15 min)

Write an algorithm that, given a length in metres, calculates and displays the equivalent in feet. You are given: 1 foot = 12 inches, 1 inch = 2.54 cm, 1 m = 100 cm.

Constraints, and these are the exercise:

  • Your algorithm must have numbered steps and explicit INPUT: / OUTPUT: lines.
  • Swap with the other pair next to you. Execute their algorithm literally, on paper, for an input of 3.5 metres. Write down the number you get by following their steps exactly — not the number you know is right.
  • If you got a different answer from theirs, find the step where the two of you diverged. That step is ambiguous. Write down which word caused it.

Hand in: your algorithm, your partner-pair’s execution of it, and the ambiguous word.
