Fundamental Relationships Between Classes

association aggregation composition dependency

Overview

Before designing class hierarchies, it is essential to understand how classes relate to one another. UML defines four fundamental inter-class relationships, each expressing a different degree of coupling and ownership. Choosing the right relationship affects object lifetime, memory management, and the overall coupling of a design.

  • Association — a general "knows about" link
  • Aggregation — a "has-a" link with independent lifetimes
  • Composition — a "has-a" link with dependent lifetimes
  • Dependency — a temporary "uses" link

Notes

Association

An association is the loosest relationship: one class holds a reference or pointer to another, but neither object owns the other. Both objects can exist independently and outlive each other.

  • Implemented as a pointer or reference member (often raw * or &)
  • The associated object is not destroyed when the holder is destroyed
  • Example: a Student associated with a Teacher — both exist in the system independently

UML notation: simple solid arrow (→)

Aggregation

Aggregation is a specialised association expressing a whole-part relationship where the part can exist without the whole. The container does not own the contained object's lifetime.

  • Typically implemented via a pointer or reference to an externally created object
  • Destroying the aggregate does not destroy the component
  • Example: a Department aggregates Employee objects — employees exist outside the department

UML notation: open diamond (◇—)

Composition

Composition is the strongest form of aggregation. The component's lifetime is strictly controlled by the composite: when the composite is destroyed, so are its parts.

  • Implemented as a by-value member or a smart pointer (std::unique_ptr)
  • The composite is solely responsible for the component's lifetime
  • Example: a Car is composed of an Engine — the engine cannot exist without the car in this design

UML notation: filled diamond (◆—)

Dependency

A dependency is a transient relationship: class A depends on class B if A uses B as a parameter type, a local variable, or a return type in one of its operations, but does not hold a persistent reference.

  • The weakest form of coupling — no member variable involved
  • Changes to B's interface may require A to be recompiled
  • Example: a Printer depends on a Document passed to its print() method

UML notation: dashed arrow (- - →)

Code Examples

Association

// Association: Student "knows about" a Teacher via a non-owning pointer.
class Teacher {
public:
    std::string name;
    Teacher(const std::string& n) : name(n) {}
};

class Student {
    Teacher* advisor; // non-owning pointer
public:
    Student(Teacher* t) : advisor(t) {}
    void greet() const {
        std::cout << "My advisor is " << advisor->name << "\n";
    }
};

int main() {
    Teacher t("Dr. Smith");
    Student s(&t);  // Teacher created externally; Student doesn't own it
    s.greet();
}

Aggregation

// Aggregation: Department holds pointers to Employee objects it does not own.
class Employee {
public:
    std::string name;
    Employee(const std::string& n) : name(n) {}
};

class Department {
    std::vector<Employee*> members; // non-owning
public:
    void add(Employee* e) { members.push_back(e); }
    void list() const {
        for (auto* e : members)
            std::cout << e->name << "\n";
    }
};

int main() {
    Employee e1("Alice"), e2("Bob");
    Department d;
    d.add(&e1);
    d.add(&e2);
    d.list();
    // e1, e2 outlive d — no double-free
}

Composition

#include <memory>

// Composition: Car owns its Engine; Engine cannot exist independently.
class Engine {
public:
    void start() { std::cout << "Engine started\n"; }
};

class Car {
    std::unique_ptr<Engine> engine; // owning — Engine destroyed with Car
public:
    Car() : engine(std::make_unique<Engine>()) {}
    void drive() { engine->start(); std::cout << "Driving\n"; }
};

int main() {
    Car car;
    car.drive();
    // When 'car' goes out of scope, engine is automatically destroyed.
}

Dependency

// Dependency: Printer uses a Document only during the print() call.
class Document {
public:
    std::string content;
    Document(const std::string& c) : content(c) {}
};

class Printer {
public:
    // Document is a parameter — no persistent reference stored
    void print(const Document& doc) const {
        std::cout << "[Printing] " << doc.content << "\n";
    }
};

int main() {
    Document d("Hello, World!");
    Printer p;
    p.print(d);
}

Exercises

Exercise 1

Model a Library system. A Library manages a collection of Book objects. Books can exist independently of the library (e.g., be on loan). Implement the correct relationship, add a method to add/remove books, and print all titles. Justify your relationship choice (association vs. aggregation vs. composition).

Exercise 2

Design a House class that is composed of Room objects. Each Room has a name and an area (in m²). The House should expose a method that returns the total floor area. Ensure that destroying a House automatically cleans up all its rooms. Use C++14 smart pointers.

Exercise 3

Identify each relationship in the following scenario and justify your answer:

  • A University offers several Course objects. Courses can exist in a catalog before any university is assigned.
  • A Course is taught by a Professor.
  • A Gradebook calculates the final grade using a GradingPolicy passed to it at call time.

For each bullet, state: association, aggregation, composition, or dependency — and implement a minimal C++14 snippet.
