Fundamental Relationships Between Classes

oop cpp uml ownership lifetime

Overview

Before designing class hierarchies, you have to answer a more basic question: how do two classes relate? UML names four fundamental relationships, and the only thing that really separates them is who owns whose lifetime. Get the relationship wrong and you get one of two bugs: a dangling pointer (you destroyed something another object still needed) or a double-free (two objects both think they own the same thing).

The four relationships, from loosest to tightest coupling:

Relationship Meaning Lifetime Typical C++ member UML
Association "knows about" independent raw * / & (non-owning) solid arrow →
Aggregation "has-a" (shared part) independent non-owning * / container of * open diamond ◇—
Composition "has-a" (owned part) dependent by-value member or unique_ptr filled diamond ◆—
Dependency "uses" transient parameter / local / return dashed arrow ⤍

Key Ideas

  • The discriminator between these relationships is lifetime ownership, not syntax.
  • Association & aggregation are non-owning: the pointed-to object outlives, or is unaffected by, the holder. Composition is owning: destroy the whole and the part dies with it.
  • "Who calls delete?" answers almost every design question on this topic.

Notes

Association — "knows about"

The loosest relationship: one object holds a non-owning pointer or reference to another. Both can exist independently and either can outlive the other.

  • Implemented as a raw pointer or reference member (non-owning by convention).
  • The associated object is not destroyed when the holder is destroyed.
  • Example: a Student knows its advisor Teacher; both live in the system independently.

UML notation: solid arrow (→)

Aggregation — "has-a", shared part

A specialised association: a whole-part link where the part can exist without the whole. The container does not control the part's lifetime.

  • Typically a non-owning pointer, or a container of non-owning pointers, to externally created objects.
  • Destroying the aggregate does not destroy the components.
  • Example: a Department aggregates Employee objects that exist outside the department.

UML notation: open diamond (◇—)

Composition — "has-a", owned part

The strongest whole-part relationship. The part's lifetime is strictly controlled by the composite: destroy the composite and its parts go with it.

  • Implemented as a by-value member or an owning std::unique_ptr.
  • The composite is solely responsible for the part's lifetime — RAII does the cleanup for free.
  • Example: a Car owns its Engine; the engine doesn't outlive the car.

UML notation: filled diamond (◆—)

Dependency — "uses"

A transient relationship: class A depends on B if A uses B as a parameter, local variable, or return type — but stores no persistent reference.

  • The weakest coupling: no member variable involved.
  • A change to B's interface may force A to recompile.
  • Example: a Printer depends on a Document only during the print() call.

UML notation: dashed arrow (- - →)

Code Examples

Full runnable programs are in examples/. The snippets below are the teaching cut.

Association

// Association: Student "knows about" a Teacher via a non-owning pointer.
class Teacher {
public:
    std::string name;
    Teacher(const std::string& n) : name(n) {}
};

class Student {
    Teacher* advisor;            // non-owning: Student does NOT delete this
public:
    Student(Teacher* t) : advisor(t) {}
    void greet() const {
        std::cout << "My advisor is " << advisor->name << "\n";
    }
};

int main() {
    Teacher t("Dr. Smith");
    Student s(&t);               // Teacher created externally; Student doesn't own it
    s.greet();
}

Aggregation

// Aggregation: Department holds non-owning pointers to Employees it did not create.
class Employee {
public:
    std::string name;
    Employee(const std::string& n) : name(n) {}
};

class Department {
    std::vector<Employee*> members;   // non-owning
public:
    void add(Employee* e) { members.push_back(e); }
    void list() const {
        for (auto* e : members) std::cout << e->name << "\n";
    }
};                                    // ~Department does NOT delete the employees

Composition

#include <memory>
// Composition: Car owns its Engine; the Engine dies with the Car.
class Engine {
public:
    void start() { std::cout << "Engine started\n"; }
};

class Car {
    std::unique_ptr<Engine> engine;   // owning — destroyed automatically with Car
public:
    Car() : engine(std::make_unique<Engine>()) {}
    void drive() { engine->start(); std::cout << "Driving\n"; }
};                                    // unique_ptr's destructor frees the Engine. No manual delete.

Dependency

// Dependency: Printer uses a Document only during print(); stores nothing.
class Printer {
public:
    void print(const Document& doc) const {
        std::cout << "[Printing] " << doc.content << "\n";
    }
};

Exercises

Exercise 1

Library (choose & justify). Model a Library that manages Book objects. Books can exist independently of the library (e.g. out on loan). Implement the correct relationship, add methods to add/remove books and print all titles, and write one sentence justifying association vs. aggregation vs. composition for your choice.

Exercise 2

House (composition + RAII). Design a House composed of Room objects, each with a name and an area (m²). Expose totalArea(). Ensure destroying a House cleans up every Room automatically. Use C++14 smart pointers — no raw new/delete.

Exercise 3

Classify (read & defend). For each scenario, state association / aggregation / composition / dependency, then implement a minimal C++14 snippet:

  1. A University offers Course objects; courses exist in a catalog before any university.
  2. A Course is taught by a Professor.
  3. A Gradebook computes a grade using a GradingPolicy passed at call time.
