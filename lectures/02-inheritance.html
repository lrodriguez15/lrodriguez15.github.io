Inheritance

oop inheritance access-specifiers protected virtual

Overview

Inheritance lets a new class (the derived class) acquire the members of an existing class (the base class), enabling code reuse and laying the groundwork for polymorphism. The derived class gets everything the base exposes, and can extend or override it.

Topic One-liner
Syntax class Derived : public Base { };
Access specifiers Controls what inherited members look like from outside
Constructor chaining Base ctor fires first; derived ctor last. Destruction is the reverse.
protected Visible inside the hierarchy; hidden from outside code
virtual destructor Required when deleting via a base pointer — the failure-first demo shows exactly why
override keyword Compile-time check that you really are overriding a virtual function

Key Ideas

  • Public inheritance models is-a. Private/protected inheritance models implemented-in-terms-of and is rare.
  • Construction order is base → derived; destruction order is derived → base. Break this mental model and you break everything.
  • A non-virtual destructor in a base class is a silent resource leak waiting to happen. Make it virtual the moment a class is designed to be subclassed.

Notes

Syntax

The general form of a derived class declaration is:

class Derived : <access-specifier> Base {
    // additional members
};

The access specifier controls the maximum visibility of inherited members outside the derived class. Most real-world hierarchies use public inheritance.

Access Specifiers in Inheritance

Inheritance kind public members of Base protected members of Base
public remain public remain protected
protected become protected become protected
private become private become private

Rule of thumb: use public when modelling is-a (a Dog is-a Animal). Private and protected inheritance model implemented-in-terms-of and are rarely needed.

Constructor and Destructor Chaining

When a derived object is created, the base constructor runs first, then the derived constructor. You pick which base constructor to call in the derived class's member initialiser list. Destruction fires in strict reverse order: derived destructor first, base destructor last.

The protected Access Level

Members declared protected behave like private to outside code but are readable and writable in derived classes. Use protected sparingly: it couples the base and derived implementations tightly, making both harder to refactor independently.

Introducing virtual

Marking a base-class member function virtual tells the compiler to dispatch calls through the object's actual runtime type rather than its declared type. This is the gateway to polymorphism (Lecture 03). For now, the one rule to internalize:

Always declare the base class destructor virtual when the class is designed to be subclassed. Without it, delete base_ptr where base_ptr points at a derived object invokes undefined behaviour — typically, the derived destructor never runs.

The override keyword (C++11) tells the compiler to verify that the function really does override a virtual in the base. If you mistype the name or get the signature wrong, you get a compile error instead of a silent new virtual.

Code Examples

Single Inheritance and Access Specifiers

#include <iostream>
#include <string>

class Animal {
public:
    std::string name;
    Animal(const std::string& n) : name(n) {}

    void breathe() const {
        std::cout << name << " is breathing\n";
    }
};

class Dog : public Animal {   // public inheritance — Dog is-a Animal
public:
    Dog(const std::string& n) : Animal(n) {}   // delegate to base ctor

    void bark() const {
        std::cout << name << " says: Woof!\n"; // 'name' is inherited
    }
};

int main() {
    Dog d("Rex");
    d.breathe();  // inherited from Animal
    d.bark();     // defined in Dog
}

Constructor Chaining

#include <iostream>

class Shape {
protected:
    double x, y;   // position — accessible in derived classes
public:
    Shape(double x, double y) : x(x), y(y) {
        std::cout << "Shape constructed at (" << x << ", " << y << ")\n";
    }
    virtual ~Shape() {   // virtual destructor — essential for polymorphism
        std::cout << "Shape destroyed\n";
    }
};

class Circle : public Shape {
    double radius;
public:
    Circle(double x, double y, double r)
        : Shape(x, y), radius(r) {   // base constructor in initialiser list
        std::cout << "Circle constructed, radius=" << radius << "\n";
    }
    ~Circle() override {
        std::cout << "Circle destroyed\n";
    }
    double area() const { return 3.14159 * radius * radius; }
};

int main() {
    Circle c(0, 0, 5);
    std::cout << "Area: " << c.area() << "\n";
    // Destructors fire in reverse: Circle first, then Shape
}

Using protected Members

#include <iostream>

class BankAccount {
protected:
    double balance;   // derived classes can read/write; outside code cannot
public:
    BankAccount(double initial) : balance(initial) {}
    double getBalance() const { return balance; }
};

class SavingsAccount : public BankAccount {
    double interestRate;
public:
    SavingsAccount(double initial, double rate)
        : BankAccount(initial), interestRate(rate) {}

    void applyInterest() {
        balance *= (1.0 + interestRate);   // direct access to protected member
    }
};

int main() {
    SavingsAccount sa(1000.0, 0.05);
    sa.applyInterest();
    std::cout << "Balance: " << sa.getBalance() << "\n";  // 1050
    // sa.balance = 0;  // ERROR: protected — not accessible outside the hierarchy
}

FAILURE FIRST — The Non-Virtual Destructor Leak

This is the trap. The code below compiles cleanly. It even runs without crashing in a simple test. But every delete through a Base* leaves Derived's destructor un-called — leaking whatever Derived owns.

Broken

// *** BROKEN — do not ship this ***
#include <iostream>

class Base {
public:
    ~Base() { std::cout << "Base destructor\n"; }      // NOT virtual
    virtual void greet() { std::cout << "Hello from Base\n"; }
};

class Derived : public Base {
public:
    ~Derived() { std::cout << "Derived destructor\n"; }
    void greet() override { std::cout << "Hello from Derived\n"; }
};

int main() {
    Base* obj = new Derived();
    obj->greet();   // correctly calls Derived::greet — virtual dispatch works
    delete obj;     // calls Base::~Base only. Derived::~Derived NEVER runs.
                    // Undefined behaviour. Any resources Derived holds are leaked.
}

The fix — one keyword:

Fixed

class Base {
public:
    virtual ~Base() { std::cout << "Base destructor\n"; }   // virtual — now safe
    virtual void greet() { std::cout << "Hello from Base\n"; }
};

With virtual ~Base(), delete obj dispatches to Derived::~Derived first, then Base::~Base. Correct and safe.

Virtual Functions Preview

#include <iostream>
#include <memory>

class Animal {
public:
    virtual void speak() const {        // virtual — runtime dispatch
        std::cout << "...\n";
    }
    virtual ~Animal() = default;
};

class Cat : public Animal {
public:
    void speak() const override {       // override — compile-time safety check
        std::cout << "Meow!\n";
    }
};

int main() {
    // Smart pointer instead of raw new/delete
    std::unique_ptr<Animal> a = std::make_unique<Cat>();
    a->speak();   // prints "Meow!" — dispatched to Cat::speak at runtime
}   // unique_ptr calls the correct destructor automatically

Exercises

Exercise 1

Vehicle hierarchy (constructor chaining + protected). Create a class Vehicle with protected members brand (string) and speed (double). Derive Car and Motorcycle from it. Each subclass should carry one additional attribute (Car: number of doors; Motorcycle: handlebar type as a string) and a method that prints full vehicle info. Use proper constructor chaining in every initialiser list. Add a virtual destructor to Vehicle.

Exercise 2

Three-level chain (trace construction/destruction order). Build the hierarchy LivingThing → Animal → Mammal. Each level adds one attribute and calls the base constructor in its initialiser list. In main, create a Mammal object and print all attributes. Add a std::cout statement to every constructor and destructor so you can see the exact call order. Run the program and record the output — then predict what the output would be if you reversed the construction order (impossible in C++, but think through why).

Exercise 3

Diagnose and fix the non-virtual destructor (read, explain, fix). The code below compiles without warnings but has undefined behaviour. Explain precisely what goes wrong, then fix it with the minimum possible change: 

class Base {
public:
    ~Base() { std::cout << "Base destructor\n"; }
    virtual void greet() { std::cout << "Hello from Base\n"; }
};

class Derived : public Base {
public:
    ~Derived() { std::cout << "Derived destructor\n"; }
    void greet() override { std::cout << "Hello from Derived\n"; }
};

int main() {
    Base* obj = new Derived();
    obj->greet();
    delete obj;   // What is the problem here?
}

After fixing, convert the example to use std::unique_ptr<Base> so the heap allocation is managed automatically.
