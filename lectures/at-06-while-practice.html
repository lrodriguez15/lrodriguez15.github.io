The while loop, in practice — one step too many, one too few

python while loops functions off-by-one euclid random week-03

Objective. Write four loops inside functions, each tested from the shell at its boundary, and name the off-by-one before running.

Overview

Tuesday gave you the loop. Today you write four of them, and every one is built around the same trap: the loop that runs once too often, or once too few. 6, not 5. 55 becoming 65. digits(0). The spec says down to 1 and the program prints 0.

Off-by-one is not a beginner’s bug. It is the bug — the one professionals still write. The cure is not care; it is a habit: before you run the loop, write down what the first turn and the last turn do. Today’s exercises are chosen so that the boundary is always where the marks are, and the shell is where you check it in four seconds.

Everything is a function with a main. That is no longer a topic; it is the format.

Opener — The shortest job first (10 min)

Algorithms to Live By, chapter 5, Scheduling. You have five things to do tonight and one evening. Which order?

Put them on the slide with their durations: reply to an email (5 min), HW4 (90 min), buy groceries (30 min), call home (15 min), read for Tuesday (40 min). Ask the room for an order and a reason. Someone will say “the urgent one first”; someone will say “the big one first, get it out of the way”.

Then the result from 1954 (W. E. Smith): if the goal is that the sum of everyone’s waiting time is as small as possible, there is exactly one right order — Shortest Processing Time first. Do the 5, then the 15, then the 30, then the 40, then the 90. Every other order makes the total wait larger. The intuition: a long task at the front makes everything behind it wait; a short task at the front makes everything wait only a little.

Compute it with them: SPT order gives completion times 5, 20, 50, 90, 180 — total 345. Longest first: 90, 130, 160, 175, 180 — total 735. Same five tasks, same evening, twice the waiting.

Now look at how you did it: while there are tasks left: pick the shortest remaining one, do it, cross it off. A loop. With a quantity that moves toward the exit — the list gets shorter every turn. (The book’s caveat: if the tasks have deadlines, the rule changes to Earliest Due Date first. Different goal, different algorithm — the goal comes first.)

Your turn, 3 minutes, on paper: write SPT as an algorithm. INPUT: a list of tasks with durations. OUTPUT: the order. The loop, the exit, and the one step that chooses. Keep it: in week 7 you will write it in Python, with a list.

Notes

The smell, revisited — what broke in the lab

Two answers from the room, no more. The ones you want: “it never stopped” (missing step, or step outside the block) and “it asked one time too many” (the test). Both are today.

Exercise 1 — countdown(n) (the test)

Open 01_countdown.py. Spec: display n, n−1, …, 1, one per line, then Liftoff!

def countdown(n):
    while n > 0:
        print(n)
        n = n - 1
    print("Liftoff!")

Shell: countdown(3) → 3 2 1 Liftoff!. countdown(1) → 1 Liftoff!. countdown(0) → just Liftoff! — the block ran zero times, and that is what the spec implies. Change the test to n >= 0 and 0 appears; the spec said down to 1. One character, one extra turn.

Notice we are changing the parameter n inside the function. That is allowed — it is the function’s own copy (A4 on Tuesday’s exam). The caller’s variable is untouched.

Exercise 2 — digits(n) (the start)

Open 02_digits.py. Spec: return how many digits a non-negative whole number has.

def digits(n):
    count = 1
    while n >= 10:
        n = n // 10
        count = count + 1
    return count

The step is n // 10 — integer division drops the last digit: 1234 // 10 is 123. Shell: digits(1000) → 4, digits(999) → 3, digits(10) → 2, digits(7) → 1.

Now the start. The obvious version starts count = 0 with while n > 0. It gives digits(0) → 0. Does zero have no digits? The spec says non-negative, so 0 is a legal input and the answer must be 1. Starting count at 1 and testing n >= 10 fixes it — every number has at least one digit, and the loop counts the extra ones. Where the counter starts is a decision about the smallest input.

Exercise 3 — play(secret) (the step order, and random)

Open 03_guess.py. The computer picks a number 1–100; the user guesses; the program says Higher or Lower; at the end, the number of attempts.

import random

def play(secret):
    attempts = 0
    guess = int(input("Guess: "))
    attempts = attempts + 1
    while guess != secret:
        if guess < secret:
            print("Higher.")
        else:
            print("Lower.")
        guess = int(input("Guess: "))
        attempts = attempts + 1
    return attempts

def main():
    secret = random.randint(1, 100)
    print("Found it in", play(secret), "attempts.")

Three things. The sentinel idiom from Tuesday, with the “sentinel” now being the right answer: first input() before the loop, the next one last inside it. The counter goes up right after each input() — put it anywhere else and you are off by one (try: move attempts = attempts + 1 above the first input()… and the count still works; move it out of the loop and it never passes 1). And random.randint(1, 100) — includes both ends. The random module is imported at the top; this is the self-study page’s first appearance in anger.

Shell test with a known secret — that is why play takes secret as a parameter instead of picking it: play(50), type 50 → 1. play(50), type 25, 75, 50 → 3. A function you can test is a function whose randomness lives in main.

Stretch 01 asked for an algorithm that always finds the number in seven questions. Play it that way: 50, then 25 or 75… How many did you need?

Exercise 4 — gcd(a, b) (termination)

Open 04_gcd.py. Euclid, 300 BC — from the stretch problems of lecture 01, now as code:

def gcd(a, b):
    while a != b:
        if a > b:
            a = a - b
        else:
            b = b - a
    return a

gcd(48, 18) → 6: 48−18 = 30, 30−18 = 12, 18−12 = 6, 12−6 = 6, equal — stop. gcd(1071, 462) → 21. gcd(7, 7) → 7 without entering the loop.

Why does it stop? Every turn makes one of the two numbers strictly smaller, and neither can go below 1 (they are positive, and we always subtract the smaller from the larger). So the sum a + b goes down every turn and cannot go below 2. Name the quantity, name the floor — that is a termination proof, and it is the only kind of argument that ever convinces anyone a loop ends.

Now break the promise: gcd(5, 0). a > b, a = 5 − 0 = 5, forever. Ctrl+C. The docstring said positive integers; the caller lied. Whose bug is it? The caller’s — and yet in main you are the caller, so main must check before it calls. That is the division of labour we have had since week 2: functions compute, main reads, checks and prints.

Stretch — if the session was easy

Optional, ungraded, harder than they look.

  1. Euclid, faster. Replace subtraction with %: while b != 0: a, b = b, a % b. Trace gcd(1071, 462) both ways and count the turns. Then argue why the % version also stops — the quantity is different. Which version would you trust with gcd(10**9, 1)?
  2. The binary search guesser. Write robot_play(secret) that plays play’s game without a human: it keeps low and high, always guesses the middle, and counts attempts. Run it for every secret from 1 to 100 (a loop around a loop) and report the maximum attempts. Is it 7? Then make the range 1–1000 and predict the maximum before running.
  3. Reverse, not count. reverse_digits(n) returns the number with its digits reversed — 1234 → 4321, 1200 → 21. Same loop as digits, with % 10 to pull the last digit and an accumulator built with `* 10 +. Then the question: for which inputs doesreverse_digits(reverse_digits(n)) != n`, and is that a bug or the spec?

Code Examples

01_countdown.py

# 01_countdown.py — "display n, n-1, ..., 1, then Liftoff!" Where is the off-by-one hiding?

def countdown(n):
    """Display n down to 1, one per line, then Liftoff!"""
    while n > 0:
        print(n)
        n = n - 1
    print("Liftoff!")


def main():
    n = int(input("Count down from: "))
    countdown(n)


main()
# countdown(3) -> 3 2 1 Liftoff!      countdown(0) -> Liftoff!      countdown(1) -> 1 Liftoff!
# Change the test to n >= 0 and watch the 0 appear. The spec said "down to 1".

02_digits.py

# 02_digits.py — how many digits does a whole number have? // is the step.

def digits(n):
    """Return the number of digits of a non-negative integer n."""
    count = 1                # every number has at least one digit — including 0
    while n >= 10:
        n = n // 10          # chop off the last digit
        count = count + 1
    return count


def main():
    n = int(input("A whole number: "))
    print("Digits:", digits(n))


main()
# digits(0) -> 1   digits(7) -> 1   digits(10) -> 2   digits(999) -> 3   digits(1000) -> 4
# The boundary is 10: count = 0 with "while n > 0" gives digits(0) -> 0. Is 0 a number with no digits?

import random


def play(secret):
    """Ask until the user finds secret. Return the number of attempts."""
    attempts = 0
    guess = int(input("Guess: "))

            print("Higher.")
        else:
            print("Lower.")

        attempts = attempts + 1

def main():

04_gcd.py

# 04_gcd.py — Euclid, the oldest algorithm in daily use (stretch problem, lecture 01), as a loop.

def gcd(a, b):
    """Greatest common divisor of two positive integers, by repeated subtraction."""
    while a != b:
        if a > b:
            a = a - b
        else:
            b = b - a
    return a


def main():
    a = int(input("First number: "))
    b = int(input("Second number: "))
    print("GCD:", gcd(a, b))


main()
# gcd(48, 18) -> 6     gcd(1071, 462) -> 21     gcd(7, 7) -> 7     gcd(1, 100) -> 1
# Why must it stop? Every turn makes one of the two numbers smaller, and neither can go below 1.
# Try gcd(5, 0) ... and keep Ctrl+C ready. The spec said POSITIVE integers.
