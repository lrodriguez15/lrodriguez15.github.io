Lecture 05 · C++14

Rule of Three

oop raii copy-semantics deep-copy rule-of-three copy-and-swap

Overview

Key Ideas

  • If a class has a custom destructor, the compiler-generated copies are almost certainly wrong.
  • A deep copy allocates new storage and copies the content, so each object owns its own resource.
  • Copy assignment has three responsibilities: guard against self-assignment, release the old resource, deep-copy the new one.
  • The copy-and-swap idiom provides strong exception safety and eliminates the self-assignment guard.
  • C++11 extended this to the Rule of Five (add move constructor + move assignment). Lecture 7 covers moves.
Special member function Signature When called
Destructor ~T() object goes out of scope / delete
Copy constructor T(const T&) initialisation from another T
Copy assignment T& operator=(const T&) assignment to an already-constructed T

The Rule of Three: if your class explicitly defines any one of the three above, it almost certainly needs all three.

Why? A custom destructor is a signal that the class manages a resource (heap memory, a file handle, a socket). The compiler-generated copy operations do a shallow copy — they copy the pointer, not what it points to. The result is two objects sharing the same allocation: the first destructor frees it, the second destructor frees it again — double-free, undefined behaviour.

Notes

Why the Compiler-Generated Copies Are Wrong

The compiler synthesises a copy constructor and copy assignment operator for every class that does not define them. For simple value types (all members are scalars or own objects) the generated versions are correct. But for a class that holds a raw pointer to a heap allocation, the generated copy does this: 

original.data ──► [ heap block ]
                        ▲
copy.data    ───────────┘        ← same pointer, same block

When either object is destroyed, the block is freed. The other object now holds a dangling pointer. When it is destroyed, the block is freed a second time: double-free.

The Destructor

Releases any resource the object acquired during its lifetime. For raw heap arrays, that means delete[]. For a single object, delete. The destructor is always the easiest of the three to write correctly; it is also the breadcrumb that tells you the other two are needed.

The Copy Constructor

Called during initialisation from an existing object: 

MyString b = a;     // copy constructor
MyString c(a);      // copy constructor
void f(MyString x); // copy constructor when passing by value

A correct copy constructor allocates fresh storage and copies the content — it does not copy the pointer value.

The Copy Assignment Operator

Called when an already-constructed object is assigned from another: 

MyString a, b;
a = b;              // copy assignment (both already exist)

Three responsibilities, in order:

  1. Self-assignment guard — if (this == &rhs) return *this;
    Without this, step 2 would free the memory that step 3 then tries to read.
  2. Release the current resource — delete[] data;
    If you skip this, the old allocation leaks.
  3. Deep-copy the new resource from rhs.

Copy-and-Swap Idiom

An elegant alternative that collapses the three responsibilities into a single, provably safe pattern:

  1. Write a non-throwing swap that exchanges every member.
  2. In operator=, take the parameter by value (invokes the copy constructor — the one hard thing you have already written correctly).
  3. Swap *this with the local copy.
  4. The old resource is released when the local copy's destructor runs at end-of-scope.

This handles self-assignment for free (both sides become the same value regardless), and the entire assignment is strongly exception-safe: if the copy constructor throws, *this is unchanged.

Code Examples

The Problem: Shallow Copy and Double-Free

Broken

// Deliberately broken — do NOT use this pattern in production.
class BadString {
    char* data;
public:
    BadString(const char* s) {
        data = new char[std::strlen(s) + 1];
        std::strcpy(data, s);
    }
    ~BadString() { delete[] data; }   // destructor defined...
    // ...but NO copy constructor or copy assignment!
    // The compiler generates shallow copies.

    void print() const { std::cout << data << "\n"; }
};

int main() {
    BadString a("hello");
    BadString b = a;      // shallow copy: b.data == a.data (SAME pointer!)
    b.print();            // "hello" — looks fine...
    // Scope ends: ~BadString() fires for b → frees the block
    //             ~BadString() fires for a → frees the SAME block → CRASH
}

Run with -fsanitize=address to see AddressSanitizer catch the double-free before it silently corrupts the heap in production.

The Fix: Rule of Three

Fixed

#include <iostream>
#include <cstring>

class MyString {
    char*       data;
    std::size_t len;

    void allocCopy(const char* s, std::size_t n) {
        data = new char[n + 1];
        std::memcpy(data, s, n + 1);
        len = n;
    }
public:
    // Constructor
    MyString(const char* s = "") { allocCopy(s, std::strlen(s)); }

    // 1. Destructor — releases the heap buffer
    ~MyString() { delete[] data; }

    // 2. Copy constructor — deep copy
    MyString(const MyString& other) {
        allocCopy(other.data, other.len);
    }

    // 3. Copy assignment — guard + release + deep copy
    MyString& operator=(const MyString& rhs) {
        if (this == &rhs) return *this;    // self-assignment guard
        delete[] data;                     // release current resource
        allocCopy(rhs.data, rhs.len);      // deep copy
        return *this;
    }

    void print() const { std::cout << data << " (len=" << len << ")\n"; }
};

int main() {
    MyString a("hello");
    MyString b = a;          // copy constructor — b gets its own allocation
    b.print();               // hello (len=5)

    MyString c("world");
    c = a;                   // copy assignment — c releases "world", copies "hello"
    c.print();               // hello (len=5)

    a.print();               // hello — a is unaffected
    // All three destructors run cleanly — no double-free
}

Copy-and-Swap Idiom

#include <algorithm>   // std::swap

class MyString {
    char*       data;
    std::size_t len;
public:
    MyString(const char* s = "");   // same constructor as above
    ~MyString() { delete[] data; }

    // Copy constructor (same deep-copy logic as above)
    MyString(const MyString& other);

    // swap — exchange every member; must not throw
    void swap(MyString& other) noexcept {
        std::swap(data, other.data);
        std::swap(len,  other.len);
    }

    // Copy-and-swap assignment: take by value → copy is already done
    MyString& operator=(MyString other) {   // other is a deep copy
        swap(other);                        // steal other's resource
        return *this;
        // other's destructor frees the OLD resource — automatically
    }
};

Taking other by value invokes the copy constructor (the one you already wrote and tested). The swap is a cheap pointer exchange. When other goes out of scope it destructs the old resource. Self-assignment is safe: you get a copy of yourself, swap with it, destroy the copy — net effect: unchanged.

Exercises

Exercise 1

DynArray (apply the Rule of Three). Implement a DynArray class that manages a dynamically allocated array of int. Store the pointer and the size. Write a proper destructor, copy constructor, and copy assignment operator (with self-assignment guard). In main, copy a DynArray, modify the copy, and verify that the original is unchanged. Run under -fsanitize=address to confirm no double-free or leak.

Exercise 2

Fix the broken Buffer. The following class has memory bugs. Identify every issue, explain what goes wrong at runtime for each, and fix the class by applying the Rule of Three: 

class Buffer {
    int* buf;
    int  size;
public:
    Buffer(int n) : size(n), buf(new int[n]()) {}
    ~Buffer() { delete[] buf; }
    int& operator[](int i) { return buf[i]; }
};

void test() {
    Buffer a(5);
    a[0] = 10;
    Buffer b(a);    // problem 1: shallow copy
    b[0] = 99;
    Buffer c(3);
    c = a;          // problem 2: shallow assignment + old buf leaked
}

Exercise 3

Copy-and-swap (refactor + justify). Rewrite your DynArray copy assignment operator from Exercise 1 using the copy-and-swap idiom. Add a swap member function and implement assignment by taking the parameter by value and swapping. Add comments explaining:

  • Why the self-assignment guard is no longer needed.
  • Why this version is exception-safe (what happens if the copy constructor throws).
