Rule of Five & Rule of Zero

move-semantics rule-of-five rule-of-zero smart-pointers raii noexcept

Overview

C++11 extended the Rule of Three with two new special member functions, giving us the Rule of Five. The Rule of Zero is the modern alternative: design classes so they own no raw resources at all — delegate everything to STL types that already implement the Rule of Five.

# Special member function Signature
1 Destructor ~T()
2 Copy constructor T(const T&)
3 Copy assignment T& operator=(const T&)
4 Move constructor T(T&&) noexcept
5 Move assignment T& operator=(T&&) noexcept
Rule Summary When to use
Rule of Five If you define any of the five, define or = default / = delete all five. Class owns a raw resource (new[], file handle, …).
Rule of Zero Define none of the five; let smart-pointer / STL members do the work. Every member already manages its own lifetime.

Key Ideas

  • An rvalue is a temporary — it will be discarded. && binds to rvalues and lets you steal resources instead of copying them.
  • std::move(x) is a cast, not a move. It signals "you may take this object's resources." After the move, the moved-from object must be in a valid but unspecified (usually null/empty) state.
  • Mark move operations noexcept — the standard library (e.g. std::vector reallocation) will prefer copies over moves when moves might throw, killing the performance benefit.
  • Rule of Zero is the goal. Rule of Five is the tool you reach for only when you genuinely need to manage a raw resource that no existing RAII wrapper covers.

Notes

Why Copies Are Expensive — The Motivation

Consider pushing Buffer objects (which own a heap array) into a std::vector. Every time the vector needs to grow, it copies every existing element to the new storage — each copy allocates a fresh array and memcpys the data. For a Buffer of 1 MB that's 1 MB of allocation + 1 MB of copying, per element, per reallocation. A vector of 1 000 Buffers may copy the first element nearly ten times by the time capacity stabilises.

The wasted work is obvious: those source objects are temporaries being destroyed immediately after the copy. We're allocating memory only to free it a microsecond later. Move semantics let us steal the heap array from the temporary instead of duplicating it.

Rvalues, Lvalues, and std::move

An lvalue is an expression that names a persistent object — it has an address and a lifetime beyond the current expression (int x, buf, vec[0]).

An rvalue is a temporary — it will be discarded after the enclosing full-expression. Examples: Buffer(1024), std::string("hello") + "!", the return value of a function.

&& (rvalue reference) can bind to rvalues, allowing resources to be transferred — stolen — rather than copied.

std::move(x) casts x to an rvalue reference. It does no moving itself; it just tells the compiler "treat x as a temporary — the caller is done with it." After the move, x must remain in a valid (destructible) state, but its value is unspecified.

Move Constructor

Transfers ownership of resources from a temporary (or explicitly moved) object. No new allocation — just pointer/handle theft: 

T(T&& other) noexcept
    : data(other.data), len(other.len)   // steal the pointer
{
    other.data = nullptr;                // leave source in valid state
    other.len  = 0;
}

Marking it noexcept is critical. std::vector::push_back checks whether the move constructor is noexcept; if it is not, the vector falls back to copying during reallocation to preserve the strong exception guarantee.

Move Assignment Operator

Like move construction, but the target object already owns a resource that must be released first: 

T& operator=(T&& other) noexcept {
    if (this == &other) return *this;   // self-move guard
    delete[] data;                       // release current resource
    data = other.data;                   // steal
    len  = other.len;
    other.data = nullptr;                // null out source
    other.len  = 0;
    return *this;
}

Common Bug: Forgetting to Null Out the Source Pointer

The single most frequent move-semantics bug is writing the move constructor without nulling out other.data:

Broken

// BROKEN move constructor — double-free waiting to happen
Buffer(Buffer&& other) noexcept
    : data(other.data), len(other.len)
{
    // BUG: other.data still points to the same heap block.
    // When 'other' is destroyed, it will delete[] the same pointer
    // that 'this' now owns — undefined behaviour / crash.
}

When other goes out of scope, its destructor calls delete[] other.data. But other.data still holds the same address that this->data now holds. Two destructors, one heap block — double-free.

Fixed

Buffer(Buffer&& other) noexcept
    : data(other.data), len(other.len)
{
    other.data = nullptr;  // <-- the critical line that prevents double-free
    other.len  = 0;
}

With nullptr, other's destructor calls delete[] nullptr, which is a no-op.

When the Compiler Generates (or Suppresses) Special Functions

Declaring any of the five suppresses automatic generation of some others:

You declare… Compiler suppresses…
Destructor auto-generated move operations (copy still generated, but deprecated)
Copy constructor or copy assignment auto-generated move operations
Move constructor or move assignment auto-generated copy operations

Use = default to explicitly request the compiler-generated version and = delete to forbid an operation. If you define any of the five, always provide all five explicitly — either implemented, = default, or = delete — so the compiler's behaviour is always intentional.

Rule of Zero

The cleanest solution is to avoid managing raw resources entirely. Use RAII wrappers as members:

  • std::unique_ptr<T> — sole ownership
  • std::shared_ptr<T> — shared ownership
  • std::vector<T>, std::string — dynamic collections and buffers

The compiler-generated copy/move/destructor will call the corresponding operations on those members, which are already correct. A class following the Rule of Zero has zero special member function definitions.

Note: std::unique_ptr is move-only. A class that contains a unique_ptr member will have its copy constructor and copy assignment implicitly deleted. If you need the class to be copyable, use std::vector or std::shared_ptr instead, or provide an explicit copy constructor that clones the pointed-to object.

The Problem: Wasteful Copy of a Temporary

Before move semantics, the only way to add an object to a container was to copy it: 

// Lecture 05 Buffer — copy-only (no move operations)
Buffer makeBuffer(std::size_t n) {
    return Buffer(n);          // constructs a temporary
}

int main() {
    std::vector<Buffer> vec;
    vec.reserve(4);

    // Each push_back copies the temporary — allocates + memcpys, then destroys the source.
    // The allocation and copy are pure waste: the source is discarded immediately after.
    vec.push_back(makeBuffer(1024));   // copy construct — wasteful!
    vec.push_back(makeBuffer(1024));   // copy construct — wasteful!
}

The fix is to give Buffer a move constructor. push_back will then steal the temporary's heap array rather than duplicating it.

Full Rule of Five Implementation

class Buffer {
    int*        data;
    std::size_t size;
public:
    // User-defined constructor
    explicit Buffer(std::size_t n)
        : data(new int[n]()), size(n) {}

    // 1. Destructor
    ~Buffer() { delete[] data; }

    // 2. Copy constructor
    Buffer(const Buffer& other)
        : data(new int[other.size]), size(other.size) {
        std::memcpy(data, other.data, size * sizeof(int));
    }

    // 3. Copy assignment
    Buffer& operator=(const Buffer& other) {
        if (this == &other) return *this;
        delete[] data;
        data = new int[other.size];
        size = other.size;
        std::memcpy(data, other.data, size * sizeof(int));
        return *this;
    }

    // 4. Move constructor — steal, then null out source
    Buffer(Buffer&& other) noexcept
        : data(other.data), size(other.size) {
        other.data = nullptr;  // <-- the critical line that prevents double-free
        other.size = 0;
    }

    // 5. Move assignment
    Buffer& operator=(Buffer&& other) noexcept {
        if (this == &other) return *this;
        delete[] data;          // release current resource
        data = other.data;      // steal
        size = other.size;
        other.data = nullptr;   // null out source
        other.size = 0;
        return *this;
    }

    std::size_t getSize() const { return size; }
    int& operator[](std::size_t i) { return data[i]; }
};

Move Enables Efficient Container Operations

#include <vector>
#include <string>
#include <iostream>

class Tag {
    std::string label;
public:
    explicit Tag(std::string s) : label(std::move(s)) {}  // move into member
    const std::string& get() const { return label; }
};

int main() {
    std::vector<Tag> tags;
    tags.reserve(3);

    tags.push_back(Tag("alpha"));           // move-constructs into vector
    tags.emplace_back("beta");              // constructs in-place — no move needed

    std::string s = "gamma";
    tags.push_back(Tag(std::move(s)));      // s transferred, not copied

    for (const auto& t : tags)
        std::cout << t.get() << "\n";
}

Rule of Zero in Practice

#include <memory>
#include <string>
#include <vector>

// No special member functions defined — the compiler generates all five correctly
// because every member already manages its own lifetime.
class Document {
    std::string              title;
    std::vector<std::string> lines;
    // Use vector<int> instead of unique_ptr<int[]> if copyability is needed.
    std::vector<int>         cache;

public:
    Document(std::string t, int cacheSize)
        : title(std::move(t))
        , cache(cacheSize, 0)
    {}

    void addLine(const std::string& line) { lines.push_back(line); }
    const std::string& getTitle() const   { return title; }
};

int main() {
    Document a("Notes", 64);
    a.addLine("First line");

    Document b = a;              // deep copy: string, vector — all correct
    Document c = std::move(a);   // move: all resources transferred cheaply
}

Explicitly Defaulting / Deleting

// Move-only type (e.g. a unique file handle)
class NonCopyable {
public:
    NonCopyable() = default;
    ~NonCopyable() = default;

    NonCopyable(const NonCopyable&)            = delete;  // forbid copy
    NonCopyable& operator=(const NonCopyable&) = delete;

    NonCopyable(NonCopyable&&)            = default;      // allow move
    NonCopyable& operator=(NonCopyable&&) = default;
};

// Copyable-but-not-reassignable value type
class ImmutableValue {
    int val;
public:
    explicit ImmutableValue(int v) : val(v) {}

    ImmutableValue(const ImmutableValue&)            = default;
    ImmutableValue& operator=(const ImmutableValue&) = delete;  // no reassignment
    ImmutableValue(ImmutableValue&&)                 = delete;
    ImmutableValue& operator=(ImmutableValue&&)      = delete;

    int get() const { return val; }
};

// Starting point — owns a raw array, needs all five special members manually:

    std::string* tracks;
